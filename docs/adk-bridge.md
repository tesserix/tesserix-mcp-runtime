# ADK bridge

The optional ADK bridge hosts an existing immutable `AgentToolView` without
copying its tools into runtime handlers. ADK remains authoritative for schemas,
export narrowing, validation, approvals, tenant lanes, ceilings, redaction, and
result codes; the runtime supplies the official Streamable HTTP listener and
its bounded response envelope.

## Install the reviewed release

The repository pins ADK 0.53.1 to its attested GitHub release wheel because the
package is not yet published through the trusted PyPI path:

    uv sync --frozen --extra adk

Core installation does not resolve or import ADK. Importing
`tesserix_mcp_runtime.adapters.adk` is safe without the extra; constructing
`ADKStreamableHTTPBridge` then explains that the extra is required.

## Compose an existing tool view

```python
from tesserix_adk.tools import ToolRegistry, tool

from tesserix_mcp_runtime.adapters.adk import ADKStreamableHTTPBridge


@tool(name="fare_for")
def fare_for(leg: str) -> dict[str, object]:
    """Price one leg."""
    return {"leg": leg, "eur": 40}


registry = ToolRegistry((fare_for,))
view = registry.view(allow=("fare_for",), agent="planner")
endpoint = ADKStreamableHTTPBridge(
    view,
    exports=("fare_for",),
    name="fares",
    version="1.0.0",
    per_tenant_calls=8,
    secrets=(),
)
```

Pass `endpoint` to `StreamableHTTPTransport.start` in place of a core
`ApplicationEndpoint`. The HTTP context provider must authenticate the gateway
and construct an immutable `CallContext`; the bridge never reads identity from
tool arguments or makes caller metadata authoritative.

The export list must be explicit and cannot exceed the view. Construction
fails before readiness if it names a tool the view cannot resolve. The visible
descriptor and fingerprint are generated by ADK, and every later discovery
must match that startup surface.

## Authority and result behavior

The authenticated `CallContext` supplies tenant, subject, run, scopes, trace,
and idempotency data. Caller `_meta` cannot replace them. The only remote entry
the bridge forwards is `tesserix/adk/tenant`, allowing ADK to reject an
authenticated caller that claims a different tenant before the tool body runs.

An ADK approval-required tool returns its original pending record and does not
execute. Refusal and failure results retain their stable ADK code but not the
tool body's message. Configured secrets and credential-shaped output remain
redacted. An unknown name and a registered-but-unexported name return the same
generic response.

## Image choice

Tool-only MCP servers can start from the smaller runtime image and install the
optional wheel during their reproducible build:

```dockerfile
FROM ghcr.io/tesserix/base-python-runtime-3.14:20260829@sha256:3854f5d9d00705b14077bf6715feb9c3bd6d1ad2e41d5594b3c09c0a74c22add
```

Processes that already need ADK `all` extras can reuse the preinstalled ADK
image. The recorded image contains `TESSERIX_ADK_VERSION=v0.53.1`:

```dockerfile
FROM ghcr.io/tesserix/base-python-adk-3.14:20260829@sha256:5a6fd1863ed7f37f3929cc596d0ec063c3077c11713cd334f14d1df2b30ef386
```

The second choice adds about 92–93 MB compressed per Linux platform. See
[`architecture/adk-bridge-size-report.json`](../architecture/adk-bridge-size-report.json)
for exact platform manifests and dependency measurements.

## Compatibility verification

The default tests remain ADK-free. Run the exact release behavior lane
separately:

    uv run --isolated --frozen --extra adk pytest -q -o addopts='' \
      compatibility/adk/test_bridge.py

ADK releases should dispatch the `adk-release` repository event with
`client_payload.release` set to the tag. A tag other than the reviewed pin
fails intentionally until the wheel attestation, public APIs, dependency
profile, size evidence, and cross-package behavior are reviewed together.

Semantic search, Registry publication, and Gateway activation are not bridge
responsibilities. Issues #18 through #25 add those stages without introducing
a second tool implementation or vector store here.
